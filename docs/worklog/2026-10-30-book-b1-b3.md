## B1. フォント名の引用

### 読んだところ

`font_family` は CSS に 2 か所で出る。`<style>` の規則（`lib/bitgram/renderers/svg/decorations.rb:31` の `theme_css`）と、`inline_styles: true`（ラスタ化のときは必ずこちら）のときの `font-family` 属性（`lib/bitgram/renderers/svg.rb:122` の `text_attributes`）。どちらも設定の文字列をそのまま埋めていた。スキーマ（`schema/bitgram.schema.json` の `svg.font_family`）は `;{}<>\` と制御文字を禁じるだけで、引用の有無は見ていない。

CSS の `font-family` は、引用なしの名前を「識別子の並び」としてだけ受け付ける。`M PLUS 1p` の `1p` は数字で始まるので識別子ではなく、宣言全体が無効になって既定の serif に落ちる。試し描きで見た現象（計画の「試し描きで分かったこと」1）はこれで説明がつく。

### やったこと

`Renderers::Svg::FontFamily.css`（`lib/bitgram/renderers/svg/font_family.rb`）を足し、上の 2 か所から呼ぶ。値をコンマで名前に分け（引用の中のコンマでは分けない）、各名前について:

- 既に `'…'` か `"…"` で囲まれている → そのまま（二重に引用しない）
- 総称ファミリ（`sans-serif`、`monospace` など） → そのまま
- 空白で区切った語がすべて CSS の識別子（`Noto Sans`、`Helvetica`） → そのまま
- それ以外 → `'…'` で囲む。中の `'` は `\'` にする

「識別子の並びなら引用しない」にしたのは、既存の設定の出力を 1 文字も変えないため。`Noto Sans` のような名前も引用したほうが安全側ではあるが、そうすると今まで通っていた定義の SVG が変わり、ゴールデンの比較（`spec/fixtures/golden/*.svg`）も書き換えになる。CSS として正しい名前は正しいまま出す、という線にした。実際、既定値 `Helvetica, Arial, 'Noto Sans CJK JP', sans-serif` の出力は変わらず、ゴールデンを含む既存の 167 例はそのまま通った。

途中で一度、引用符をどこでも「引用の始まり」と数える分割を書いたが、`O'Neil 2, Arial` のように名前の途中に `'` があると後ろのコンマで分けられなくなる。引用の始まりは名前の先頭（空白を除く）だけ、に直した。

### 確かめたこと

rspec に `spec/bitgram/renderers/font_family_spec.rb`（4 例）。`M PLUS 1p` → `'M PLUS 1p'`、既に引用済みのものと既定値は不変、引用の中のコンマ、`<style>` と inline 属性の両方に出ること。

試し描きの `header.yml` の `font_family` を引用なしの `M PLUS 1p` に戻して描き（`impl-b1b3/header_unquoted.yml`）、SVG を HTML に包んで Chromium で PDF にした。CSS は `font-family: &apos;M PLUS 1p&apos;;` になり、PDF のフォントは次のとおり M PLUS 1p が埋め込まれた。

```
$ python3 impl-b1b3/pdfcheck.py impl-b1b3/b1_header.pdf
pages 1
page 0 MediaBox [0.0, 0.0, 504.0, 113.040001]
  /F4 /Type0 /CIDFontType2 /AAAAAA+MPLUS1p-Regular ['/FontFile2']
```

（MediaBox の高さ 113.04 は 150px × 0.75 = 112.5 と合っていない。これは B2 で調べた。）

## B1. 本の既定設定（`--config`）

### 方式の判断

計画の案は「`--config PATH`」と「定義の `extends: PATH`」。既存の設定の合成を読んで `--config` にした。

読んだところ: `Bitgram.build`（`lib/bitgram.rb`）が定義（`source.data`）に上書き（CLI の専用オプションと `--set`、API のキーワード）を `Config.deep_merge` で重ね、`Normalizer#call`（`lib/bitgram/normalizer.rb:7`）が組み込みの `Config::DEFAULTS` の上に結果を重ねる。つまり既にある層は「組み込み既定 < 定義 < 専用オプション < `--set`」の一列で、どの層も `deep_merge` で重なる。共通設定は「組み込み既定と定義の間」に 1 層差し込めば済み、合成の仕組みには手を入れずに足せる。

`extends` にしなかった理由:

- 定義の形式（スキーマのトップレベル）が変わる。fork の定義が本家の bitgram やスキーマを使うエディタで通らなくなる。`--config` なら図の定義は本家の形式のまま。
- 定義の中から別のファイルを読むことになり、相対パスの基準（定義の場所か、カレントか）、`Bitgram.load(文字列)` のときの基準、連鎖や循環の扱いを決める必要が出る。どれも本の用途には要らない。
- 本の側（計画 B6 の `bitgram2pdf.sh`）は、全部の図を同じスクリプトで変換する。共通の設定はスクリプトが 1 か所で `--config` を渡せばよく、図ごとに書く必要がそもそも無い。

却下した理由の裏返しとして、`--config` の弱点は「`bitgram render x.yml` を素で叩くと本の設定が乗らない」こと。本の図は B6 のスクリプトから作る前提なので、ここは受け入れた。

### やったこと

- `Config.read_shared`（`lib/bitgram/config.rb`）: パスか Hash を受け取り、トップレベルが `layout` / `ascii` / `svg` / `raster` だけであることを確かめる（`fields` などがあれば ParseError）。値は定義と同じ Validator に、仮の `version` と 1 欄を足して通し、エラーは設定ファイル自身の行番号つきで ParseError にする。行番号を定義側に混ぜると、定義の別の行を指してしまうため。
- `Bitgram.compose`（`lib/bitgram.rb`）: 層を「共通設定 < 定義 < 上書き」で重ねる。`load` / `load_file` / `validate_file` に `config:` キーワードを足し、`preset` はキーワードがそのまま `load_file` に渡る。
- CLI: `render` と `validate` に `--config PATH`。`validate` は今まで上書きを何も受け取っていなかったが、共通設定（例: `allow_partial_row`）で警告が変わりうるので渡すことにした。

テーマのパスは今までどおりカレントディレクトリから解決する（設定ファイルの場所からにはしない）。本の側では、色は既存の `mono` テーマ（線 `#000000`、塗り `#ffffff`、文字 `#000000`）がそのまま合うので、テーマのファイルを作る必要は今のところ無い。文字の大きさの既定値はこの段階では決めていない（B6 で、本の図の倍率と draw.io の図の 10〜11pt から導く）。

### 確かめたこと

`spec/bitgram/shared_config_spec.rb`（6 例）: 共通設定が定義の下に入る（`font_size` は定義の 14 が勝つ）、Hash でも渡せる、`--set` が両方に勝つ、`validate --config` で V-08 の警告が消える、`fields` を含む設定は拒否、不正な値は `bad.yml:3: V-03 $.svg.font_size` のように設定ファイルの行で報告。

## B2. PDF 出力

### 方式

計画どおり、ヘッドレス Chromium の `--print-to-pdf` で、SVG を包んだ HTML を印刷する（`lib/bitgram/pdf/chromium.rb`）。新しい gem は足していない。ラスタ化と同じく SVG は `inline_styles: true` で描く（`theme: auto` の `@media` に左右されないため。`Diagram#save_raster` と同じ扱い）。`Diagram#save` に `pdf` を足し、CLI は `.pdf` の拡張子か `-f pdf` で選ぶ。PNG・JPEG と同じく出力先のパスが要る。Chromium が見つからない・失敗した・時間切れは、既存の `RasterizeError` の系統（終了コード 3）に載せた。タイムアウトは計画どおり `raster.timeout` を使い、PDF 用の別の値は作っていない。

設定は新しい `pdf` 節（スキーマの `$defs/pdf`）: `chrome`（実行ファイルのパス）、`page_step`（後述）、`sandbox`。Chromium の探し方は `pdf.chrome` → 環境変数 `BITGRAM_CHROME` → PATH 上の `chromium` / `chromium-browser` / `google-chrome` / `google-chrome-stable` / `chrome` → `~/.cache/ms-playwright/*/chrome-linux64/chrome` の番号が最大のもの。環境変数も用意したのは、機械ごとに違うパスを図の定義や共通設定に書かずに済ませるため。`bitgram doctor` に見つかった Chromium を 1 行出す。

### 試して捨てたこと: `--user-data-dir`

最初は、他の Chromium と profile を取り合わないように `--user-data-dir=<一時ディレクトリ>` を付けた。これで **PDF が書かれず、プロセスが終わらない**（40 秒のタイムアウトまで待って rc=124、出力ファイル無し）。短いパス（`/dev/shm/bgprof`）でも、`--no-first-run --disable-extensions --disable-sync --disable-background-networking --disable-component-update` を足しても同じだった。一方、`--user-data-dir` を付けなければ 0.4 秒ほどで `9646 bytes written to file ...` と出て終わる。`~/.config/google-chrome-for-testing` には `Crash Reports` しか無く、`--user-data-dir` 無しのときは Chromium が自分で一時 profile を作って消しているように見える（推測。Chromium の挙動の根拠は読んでいない）。並行実行で profile を取り合う心配は無さそうなので、`--user-data-dir` は付けないことにした。

### `--no-sandbox` を既定にしなかった

依頼のメモでは `--no-sandbox --disable-gpu` 付きで確認されていたが、この機械（WSL2、一般ユーザー）では `--no-sandbox` 無しでも同じ PDF（9646 bytes）が書けた。sandbox を外すのは安全側ではないので既定では付けず、root やコンテナで要るときのために `pdf.sandbox: false` で付けられるようにした。`--disable-gpu` はヘッドレスでは害が無いので常に付ける。

### ページの寸法: Chromium は寸法を丸める

計画は「`@page` の寸法は SVG の幅・高さを切り上げ」だった。B1 の確認で、150px の高さを指定した PDF の MediaBox が 112.5pt ではなく 113.04pt になっていたので、Chromium がページの寸法をどう扱うかを測った（`impl-b1b3/pagesize/`、`@page { size: Wpx Hpx; margin: 0 }` の HTML を印刷して pypdf で MediaBox を読む）。

```
指定(px)  期待(pt)  MediaBox(pt)
96        72.0      72.0
97        72.75     72.959999
98        73.5      73.919998
99        74.25     73.919998    ← 期待より小さい
100       75.0      75.119995
104       78.0      78.0
107       80.25     79.919998    ← 期待より小さい
108       81.0      81.119995
112       84.0      84.0
150       112.5     113.040001
151       113.25    113.040001   ← 期待より小さい
300       225.0     224.87999
```

単位を `pt` / `in` / `mm` に替えても（`112.5pt`、`1.5625in`、`39.6875mm`）同じ 113.04 になったので、単位の換算ではなく Chromium の内部で量子化されている。8px の倍数を 8〜1992px の 24 通り試すと全部ちょうど（px × 0.75）になり、8 の倍数でない 103、105、107、109、110、111px はどれもずれた。規則の出どころ（Chromium のどのコードか）は調べていないので、「8px（6pt）の倍数ならちょうど」は測った事実としてだけ扱う。

これを受けて、ページの寸法は「SVG の寸法を `pdf.page_step` px の倍数に切り上げる」にし、既定値を 8 にした（`Config::DEFAULTS` にコメントで出どころを 1 行）。SVG はページの中央に置く（余白が片側に寄らないように）。ずれは最大 7px（5.25pt）の白い余白で、SVG 自体は既定で 16px の余白を持っている。`page_step: 1` にすると計画どおりの「整数 px に切り上げ」になるが、MediaBox は Chromium の丸めのぶん（最大 1px 程度、下向きもある）ずれる。下向きに丸められる高さ（99px、107px、98.6px）でも `overflow: hidden` と固定の高さで **1 ページ** のままであることを確かめた。

```
height="99"   → pages 1, MediaBox [0, 0, 509.04, 73.92]
height="107"  → pages 1, MediaBox [0, 0, 515.04, 79.92]
height="98.6" → pages 1, MediaBox [0, 0, 509.04, 73.92]
```

計画の確認項目「MediaBox が SVG の寸法（px × 0.75 pt）に一致」は、正確には「MediaBox が（SVG の寸法を 8px の倍数に切り上げた値）× 0.75pt に一致」になった。SVG の寸法が 8 の倍数のとき（RITE ヘッダの高さ 264px など）は SVG の寸法そのものと一致する。

`spec/bitgram/pdf_spec.rb`（6 例）: ページ寸法の切り上げと HTML、Chromium の探し方（設定 → 環境変数）、見つからないときの `RasterizerNotFound`、CLI で出力先が無いときのエラー、実際の PDF（1 ページ、MediaBox、フォントが `/FontFile2`、M PLUS 1p が入っていればその名前）、CLI の `--config` 経由の PDF。Chromium か python3 の pypdf が無ければ skip する。既存の `spec/bitgram/diagram_spec.rb` は「未知の拡張子」の例として `x.pdf` を使っていたので `x.bmp` に替えた（`.pdf` が未知でなくなったため。既存の挙動を変えた唯一の箇所）。

## B3. 欄を LSB から書く（`layout.field_order`）

### 読んだところ

`Layout::Engine#call`（`lib/bitgram/layout/engine.rb:12`）は欄を書いた順に左の列から詰め、行が埋まると次の行に移る。`bit_order: lsb0` が変えるのはビット番号の表示（`renderers/svg/decorations.rb:57`、`renderers/ascii.rb` の `header`）だけで、欄の並びには触れない。計画の「試し描きで分かったこと」4 の現象はこれで、C のビットフィールド（`MRB_OBJECT_HEADER` は `include/mruby/object.h:10-15` で `tt:8; gc_color:3; frozen:1; flags:20` の順。宣言順が LSB から、というのは一般的な ABI の割り付けでの話で、C の規格は割り付け順を処理系定義にしている）を宣言順に書くと左右が逆になる。

### やったこと

`layout.field_order`（`msb_first` = 今の挙動 / `lsb_first`）を足した。`lsb_first` では、行への詰め方は今までと同じ（書いた順にビット位置 0 から）にしておき、できた行をそれぞれ左右反転する（`Engine#mirror`。各セルの列を `row_bits - col - bits` にし、セルの並びも逆にして列の昇順を保つ）。こうすると:

- 1 行に収まる構造体は、最初の欄が右端（bit 0 側）に来る
- 行をまたぐ欄は、前の行の左端（上位）から次の行の右端（下位）へ続く。下位から上位へ流れる語の並びとして自然な形
- オフセット（`offset_bits`）と分割した欄の範囲（`[0:3]` など欄の中での相対位置）は変わらない
- 最後の行が欠けているとき（`allow_partial_row`）、空きは左（上位のビットが無い側）に出る

最後の点のために ASCII の描画（`Renderers::Ascii#row_lines`）が、空きは常に右にあると仮定していたのを直した（`pad`。セルの最初の列が 0 でなければ左に空白を出す）。`msb_first` では最初の列は常に 0 なので出力は変わらない。SVG の描画はセルの列から x を計算しているので手を入れずに済んだ。

境界を描く `BoxChars.border`（`renderers/ascii/box_chars.rb:39`）もセルの列から境界を作っているので、反転後の列でそのまま正しく描ける。

### 一度入れて戻したこと: `Config::DEFAULTS` に既定値を書く

最初は `Config::DEFAULTS["layout"]` に `"field_order" => "msb_first"` を足した。テストは全部通ったが、`Model::Document#to_h` が `layout` の Hash ごと SVG の id の接頭辞のハッシュ（`Renderers::Svg#default_prefix`、題の無い図だけで使われる）に入るので、**題の無い図の id が変わる**ことに気づいた。

```
upstream eeb5ae3:                    id="bitgram-408ce7c0-diagram"
DEFAULTS に field_order を足した版:   id="bitgram-d8820472-diagram"
DEFAULTS から外した版:               id="bitgram-408ce7c0-diagram"
```

（入力は `{version: 1, fields: [{name: "A", bits: 32}]}`。upstream は `git worktree add --detach` で別ディレクトリに出して比べた。）既存のテストは題のある図しか固定していないので、これは見逃されていた。既定値は DEFAULTS に書かず、未指定は `msb_first` として扱う（エンジンは `"lsb_first"` のときだけ反転する）。B2 の `pdf` 節の既定値は DEFAULTS にあるが、`Model::Document` には入らない（`Normalizer` が `pdf` を Document に渡さない）ので id には効かない。

念のため、`spec/fixtures/valid/*` と同梱の preset の 15 個の定義を、upstream と今の版の両方で SVG と ASCII に描いて md5 を比べ、30 通りすべて一致した。

### 確かめたこと

## 気づいた点（範囲外。直していない）

- **id の接頭辞が設定に依存する**（`lib/bitgram/renderers/svg.rb` の `default_prefix`）。題の無い図では `Model::Document#to_h`（layout・ascii・svg・raster の全設定を含む）のハッシュが id になるため、`Config::DEFAULTS` に新しい既定値を足すだけで既存の図の id が変わる。本家に設定を足すときの落とし穴。属する先: 本家への PR を考えるとき（計画の「本家への PR は本が出た後」）。
- **脚注の連番は表示の左から**（`Text::Fitter` は描く順に番号を振る）。`lsb_first` のオブジェクトヘッダでは `frozen` が `*1`、`gc_color` が `*2` になり、宣言順（tt, gc_color, frozen, flags）とは逆になる。B4（細い欄の名前）で脚注の扱いを決めるときに合わせて見る話。
- **Chromium の `--user-data-dir` でハングする**（B2 の節）。原因は調べていない。本の側（B6）の `drawio2pdf.sh` のように他のツールから Chromium を呼ぶときにも同じことが起きうる。
- **PNG のラスタ化器（vips / rsvg / ImageMagick）がこの機械に無い**ので、`bitgram render -o x.png` は使えない（rspec の pending 5 件の理由）。B6 で PDF から PNG を作る段は、Chromium の `--screenshot` か別の道具が要る。属する先: B6。
- 文字の大きさの既定値（本の draw.io の図は 10〜11pt）は決めていない。PDF の 1px は 0.75pt なので、Re:VIEW で `scale=1.0` で載せるなら 10〜11pt は 13.3〜14.7px（今の既定 `font_size: 13` は 9.75pt）。図の幅が本文幅（約 441pt = 588px）を超えると縮小されるので、実際の大きさは図の幅と倍率で決まる。属する先: B6。
