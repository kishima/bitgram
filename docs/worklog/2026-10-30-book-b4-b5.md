## B4. 細い欄の名前

### 読んだところ

欄の名前を枠に収める処理は `Text::Fitter#fit`（`lib/bitgram/text/fitter.rb`）で、`fit_order` の戦略を順に試し、最初に収まったものの `FitResult`（行、文字の大きさ、戦略、脚注）を返す。SVG は `Renderers::Svg#fit_cell` で枠ごとに呼び、`Svg::Geometry#row_height` が結果の行数から行の高さを決め、`Svg::Cells#draw_label` が枠の中央に行を並べる。

既存の戦略のうち、細い欄に関わるのは 3 つ。

- `vertical`: 1 文字ずつ縦に積む（`multiline`）。行数の上限は `ascii.max_label_lines`（既定 4）で、SVG も同じ値を使う。`frozen`（6 文字）は 4 を超えるので落ちる。
- `footnote`: 枠に `*1` を出し、名前を図の下に回す。`*1` が幅に収まらないと 1 文字ずつに分けて縦に積む（`marker.scan(/\X/)`）。B3 の PNG で `frozen` が `*` と `1` の 2 行になっていたのはこれ。
- `shrink`: `font_size` から 0.5px ずつ `min_font_size` まで下げる。`gc_color`（3bit、内幅 52px）は 10.5px で収まる（8 文字 × 10.5 × 0.6 = 50.4）ので、既定の順では `shrink` で描かれる。1bit（内幅 12px）は 9px でも 1 文字 5.4px なので 2 文字までしか入らない。

### やったこと

計画の 3 案を、`svg.fit_order` に書ける戦略として足した。既定の `fit_order` は変えていない。どれも文字の大きさを使うので SVG だけのもので、スキーマでも `svg.fit_order` の列挙にだけ足した（`ascii.fit_order` には書けない。`Fitter` は文字の大きさが無いとき、この 3 つを「収まらない」として次の戦略へ進む）。`svg.fit_order` の `maxItems` は 7 から 10 にした。これは戦略の数そのもので、全部を 1 回ずつ書ける長さ（`uniqueItems`）。

- `leader`（案 a、引き出し線）: 枠の中は空にして、名前を行の下に出し、枠の下辺の中央から縦の線でつなぐ。行の下に帯を足し、その高さは `svg.leader_gap` と、名前の段の数 ×（`font_size` × 1.2）。1.2 は折り返した名前の行送りとして既に使われている値（`Geometry#row_height`、`Cells#draw_label`）。
- `rotate`（案 b、縦書き）: 名前を 90 度回して（下から上へ読む）枠の中に出す。回すと行の高さが枠の幅に収まる必要があるので、`font_size` から 0.5px ずつ `min_font_size` まで、行の高さ（文字の大きさ）が枠の内幅以下になる最大の大きさを使う。名前の長さぶん行が高くなる。
- `footnote_shrink`（案 c、脚注を 1 行で）: `footnote` と同じく脚注に回すが、印（`*1`）を 1 行のまま、収まる最大の大きさ（`min_font_size` まで）で出す。番号は `footnote` と共通。

既存の `vertical` を「縦書き」として使う案は採らなかった。`vertical` は 1 文字ずつ積む形で、行数の上限が ASCII と共通の `max_label_lines` なので、SVG の側だけで上限を外すと ASCII との意味がずれる。読みやすさの点でも、英字の名前は回したほうが単語のまま読める。

`rotate` の大きさの条件を「文字の大きさ ≤ 枠の内幅（枠の幅 − 8）」にしたのは、横書きの名前と同じ内幅で判断するため。既定（`bit_width` 20、内幅 12）では 13px の名前は 12px になる。枠の幅（20）で判断すれば 13px のまま入るが、既存の戦略がどれも内幅で判断しているのに合わせた。

`leader` の名前の置き方（`lib/bitgram/renderers/svg/leaders.rb`）。1 行に引き出しが複数あるとき、名前どうしが重ならず、線が他の名前を横切らないように段を分ける。名前は線を中心にするか、線の少し右から始めるか、少し左で終えるかの 3 通りを試し、図の幅の中に収める。最初は「左から順に、最初に空いている段に置く」だけにしたが、テストで次の形が解けなかった: 左端の 1bit 欄 2 つ（線が 20px 間隔）に 40px の名前を付けると、左の名前が段 0 に置かれた時点で右の線がその名前の下を通るしかなくなり、どの段にも置けない。右の名前を段 0、左を段 1 にすれば解ける。そこで「左から・中心優先」「右から・右寄せ優先」「左から・左寄せ優先」の 3 通りの順で置いてみて、線が名前を横切った数、段の数の少ない順で選ぶことにした。どの順でも置けないとき（名前が幅に対して多すぎるとき）は一番下の段に置き、線が名前を横切る。3 つの 40px の名前を 20px 間隔の線に付ける形は、まっすぐな線では解が無い（中央の名前の段 0 の位置が両隣の線を必ず覆う）ことを手で確かめたので、テストには解のある形だけを入れた。

欄に `value` があるとき、値は枠の中に残す（値の戦略の順からは `leader` を除く）。名前だけが下に出る。

`svg.leader_gap` の既定 8 は、bitgram が表と脚注の間に空けている 8px（`Geometry#footer_height`、`Svg#draw_footer`）と同じにした。測って決めた値ではない。既定値は B3 と同じ理由で `Config::DEFAULTS` には書かず、使う場所で `@options.fetch("leader_gap", 8)` としている（DEFAULTS の `svg` に足すと、題の無い図の id のハッシュに入って変わる）。

### 合字（`svg.ligatures`）

本体のレビューで、M PLUS 1p では `flags` の `fl` が合字（U+FB02）になると指摘があった。`svg.ligatures: false` を足し、`<style>` の `text` の規則に `font-variant-ligatures: none;` を、`inline_styles: true`（PDF とラスタ化のとき）では各 `<text>` に `style="font-variant-ligatures: none"` を付ける。既定（未指定、または `true`）では何も出さず、出力は今までと同じ。`font-variant-ligatures` は SVG の表示属性に無いので、属性ではなく `style` に書いた。

PDF で切れていることを、pypdf の抽出テキストで確かめた。`book.yml` は `book_liga.yml` に `ligatures: false` を足したもの。

```
$ bundle exec exe/bitgram render header_leader.yml --config book.yml -o header_leader.pdf
$ bundle exec exe/bitgram render header_leader.yml --config book_liga.yml -o header_leader_liga.pdf
== header_leader（ligatures: false）
'オブジェクトヘッダのビットフィールド（tt から flags までの 32bit）\n31 30 … 1 0\nflags gc_color tt\nfrozen'
  /F4 /Type0 /CIDFontType2 /AAAAAA+MPLUS1p-Regular ['/FontFile2']
== header_leader_liga（指定なし）
'オブジェクトヘッダのビットフィールド（tt から ﬂags までの 32bit）\n31 30 … 1 0\nﬂags gc_color tt\nfrozen'
  /F4 /Type0 /CIDFontType2 /AAAAAA+MPLUS1p-Regular ['/FontFile2']
```

指定なしでは `ﬂags`（U+FB02 の 1 文字）、`ligatures: false` では `flags` の 5 文字。PNG でも `f` と `l` が離れているのを目で見た。

### lsb_first のときの脚注の番号

`Text::Fitter` は描く順（行ごとに左から）に番号を振る。`field_order: lsb_first` では各行を左右反転して描くので、番号は定義に書いた順（C の宣言順）とは逆になる。例えば 2 つの 1bit 欄を `a, b` の順に書くと、右端の `a` が `*2`、その左の `b` が `*1` になる。

番号は描いた順（左から）のままにした。読者が見るのは図であって定義ではなく、図の中の印は左から `*1`、`*2` と読めるのが自然で、図の下の脚注の並びとも合う。定義の順で振る選択肢（例えば `footnote_order` の設定）は足していない。オブジェクトヘッダで脚注になるのは `frozen` 1 つなので、本の図で問題になる場面がまだ無いため。この扱いは `docs/format.md` の Label fitting に 1 文書いた。

### 3 案の PNG

オブジェクトヘッダ（`tt` 8bit、`gc_color` 3bit、`frozen` 1bit、`flags` 20bit、`field_order: lsb_first`、`bit_order: lsb0`、M PLUS 1p、`theme: mono`、`ligatures: false`）を 3 案で描いた。定義は B3 の `header.yml` に `svg.fit_order` を 1 行足しただけ。PNG は前の担当の `screenshot.rb`（PDF と同じ HTML を Chromium の `--screenshot`、倍率 2）。

| 案 | `svg.fit_order` | PNG |
|---|---|---|
| (a) 引き出し線 | `[single, shrink, wrap, short, leader, truncate]` | `impl-b4b5/header_leader.png` |
| (b) 縦書き | `[single, shrink, wrap, short, rotate, truncate]` | `impl-b4b5/header_rotate.png` |

既定の順に倣って `shrink` を前に置いたので、どの案でも `gc_color` は縮小（10.5px）で枠に収まり、新しい戦略を使うのは `frozen` だけになる。`gc_color` も同じ戦略で描いた形を比べられるように、`shrink` を外した `[single, <案>, truncate]` も描いた（`header_leader_noshrink.png`、`header_rotate_noshrink.png`、`header_footnote_noshrink.png`）。縦書きでは `gc_color` が 13px のまま回り、行が 154px の図になる。引き出し線では `frozen` と `gc_color` が同じ段に並ぶ。

### 確かめたこと

`spec/bitgram/renderers/narrow_labels_spec.rb`（7 例）: `leader` の線の位置（`frozen` の枠の中央 x=426）と帯の高さ（8 + 15.6）、`leader_gap` で線の長さが変わること、`rotate` の `transform` と 12px への縮小と行の高さ 51.2、`footnote_shrink` の 1 行の印（10px）と脚注、文字の大きさが無い（ASCII の）`Fitter` で 3 つとも次へ進むこと、値が枠に残ること、引き出しの名前の置き方（隣り合う 2 つが別の段になり、線が名前を横切らない。右端でも図の幅に収まる）、合字の設定が CSS と inline の両方に出て、既定では出ないこと。
