## B4. 細い欄の名前

### 読んだところ

欄の名前を枠に収める処理は `Text::Fitter#fit`（`lib/bitgram/text/fitter.rb`）で、`fit_order` の戦略を順に試し、最初に収まったものの `FitResult`（行、文字の大きさ、戦略、脚注）を返す。SVG は `Renderers::Svg#fit_cell` で枠ごとに呼び、`Svg::Geometry#row_height` が結果の行数から行の高さを決め、`Svg::Cells#draw_label` が枠の中央に行を並べる。

既存の戦略のうち、細い欄に関わるのは 3 つ。

- `vertical`: 1 文字ずつ縦に積む（`multiline`）。行数の上限は `ascii.max_label_lines`（既定 4）で、SVG も同じ値を使う。`frozen`（6 文字）は 4 を超えるので落ちる。
- `footnote`: 枠に `*1` を出し、名前を図の下に回す。`*1` が幅に収まらないと 1 文字ずつに分けて縦に積む（`marker.scan(/\X/)`）。B3 の PNG で `frozen` が `*` と `1` の 2 行になっていたのはこれ。
- `shrink`: `font_size` から 0.5px ずつ `min_font_size` まで下げる。`gc_color`（3bit、内幅 52px）は 10.5px で収まる（8 文字 × 10.5 × 0.6 = 50.4）ので、既定の順では `shrink` で描かれる。1bit（内幅 12px）は 9px でも 1 文字 5.4px なので 2 文字までしか入らない。

### やったこと

計画の 3 案を、`svg.fit_order` に書ける戦略として足した。既定の `fit_order` は変えていない。どれも文字の大きさを使うので SVG だけのもので、スキーマでも `svg.fit_order` の列挙にだけ足した（`ascii.fit_order` には書けない。`Fitter` は文字の大きさが無いとき、この 3 つを「収まらない」として次の戦略へ進む）。`svg.fit_order` の `maxItems` は 7 から 10 にした。これは戦略の数そのもので、全部を 1 回ずつ書ける長さ（`uniqueItems`）。

- `leader`（案 a、引き出し線）: 枠の中は空にして、名前を行の下に出し、枠の下辺の中央から縦の線でつなぐ。行の下に帯を足し、その高さは `svg.leader_gap` と、名前の段の数 ×（`font_size` × 1.2）。1.2 は折り返した名前の行送りとして既に使われている値（`Geometry#row_height`、`Cells#draw_label`）。
- `rotate`（案 b、縦書き）: 名前を 90 度回して（下から上へ読む）枠の中に出す。回すと行の高さが枠の幅に収まる必要があるので、`font_size` から 0.5px ずつ `min_font_size` まで、行の高さ（文字の大きさ）が枠の内幅以下になる最大の大きさを使う。名前の長さぶん行が高くなる。
- `footnote_shrink`（案 c、脚注を 1 行で）: `footnote` と同じく脚注に回すが、印（`*1`）を 1 行のまま、収まる最大の大きさ（`min_font_size` まで）で出す。番号は `footnote` と共通。

既存の `vertical` を「縦書き」として使う案は採らなかった。`vertical` は 1 文字ずつ積む形で、行数の上限が ASCII と共通の `max_label_lines` なので、SVG の側だけで上限を外すと ASCII との意味がずれる。読みやすさの点でも、英字の名前は回したほうが単語のまま読める。

`rotate` の大きさの条件を「文字の大きさ ≤ 枠の内幅（枠の幅 − 8）」にしたのは、横書きの名前と同じ内幅で判断するため。既定（`bit_width` 20、内幅 12）では 13px の名前は 12px になる。枠の幅（20）で判断すれば 13px のまま入るが、既存の戦略がどれも内幅で判断しているのに合わせた。

`leader` の名前の置き方（`lib/bitgram/renderers/svg/leaders.rb`）。1 行に引き出しが複数あるとき、名前どうしが重ならず、線が他の名前を横切らないように段を分ける。名前は線を中心にするか、線の少し右から始めるか、少し左で終えるかの 3 通りを試し、図の幅の中に収める。最初は「左から順に、最初に空いている段に置く」だけにしたが、テストで次の形が解けなかった: 左端の 1bit 欄 2 つ（線が 20px 間隔）に 40px の名前を付けると、左の名前が段 0 に置かれた時点で右の線がその名前の下を通るしかなくなり、どの段にも置けない。右の名前を段 0、左を段 1 にすれば解ける。そこで「左から・中心優先」「右から・右寄せ優先」「左から・左寄せ優先」の 3 通りの順で置いてみて、線が名前を横切った数、段の数の少ない順で選ぶことにした。どの順でも置けないとき（名前が幅に対して多すぎるとき）は一番下の段に置き、線が名前を横切る。3 つの 40px の名前を 20px 間隔の線に付ける形は、まっすぐな線では解が無い（中央の名前の段 0 の位置が両隣の線を必ず覆う）ことを手で確かめたので、テストには解のある形だけを入れた。

欄に `value` があるとき、値は枠の中に残す（値の戦略の順からは `leader` を除く）。名前だけが下に出る。

`svg.leader_gap` の既定 8 は、bitgram が表と脚注の間に空けている 8px（`Geometry#footer_height`、`Svg#draw_footer`）と同じにした。測って決めた値ではない。既定値は B3 と同じ理由で `Config::DEFAULTS` には書かず、使う場所で `@options.fetch("leader_gap", 8)` としている（DEFAULTS の `svg` に足すと、題の無い図の id のハッシュに入って変わる）。

### 合字（`svg.ligatures`）

本体のレビューで、M PLUS 1p では `flags` の `fl` が合字（U+FB02）になると指摘があった。`svg.ligatures: false` を足し、`<style>` の `text` の規則に `font-variant-ligatures: none;` を、`inline_styles: true`（PDF とラスタ化のとき）では各 `<text>` に `style="font-variant-ligatures: none"` を付ける。既定（未指定、または `true`）では何も出さず、出力は今までと同じ。`font-variant-ligatures` は SVG の表示属性に無いので、属性ではなく `style` に書いた。

PDF で切れていることを、pypdf の抽出テキストで確かめた。`book.yml` は `book_liga.yml` に `ligatures: false` を足したもの。

```
$ bundle exec exe/bitgram render header_leader.yml --config book.yml -o header_leader.pdf
$ bundle exec exe/bitgram render header_leader.yml --config book_liga.yml -o header_leader_liga.pdf
== header_leader（ligatures: false）
'オブジェクトヘッダのビットフィールド（tt から flags までの 32bit）\n31 30 … 1 0\nflags gc_color tt\nfrozen'
  /F4 /Type0 /CIDFontType2 /AAAAAA+MPLUS1p-Regular ['/FontFile2']
== header_leader_liga（指定なし）
'オブジェクトヘッダのビットフィールド（tt から ﬂags までの 32bit）\n31 30 … 1 0\nﬂags gc_color tt\nfrozen'
  /F4 /Type0 /CIDFontType2 /AAAAAA+MPLUS1p-Regular ['/FontFile2']
```

指定なしでは `ﬂags`（U+FB02 の 1 文字）、`ligatures: false` では `flags` の 5 文字。PNG でも `f` と `l` が離れているのを目で見た。

### lsb_first のときの脚注の番号

`Text::Fitter` は描く順（行ごとに左から）に番号を振る。`field_order: lsb_first` では各行を左右反転して描くので、番号は定義に書いた順（C の宣言順）とは逆になる。例えば 2 つの 1bit 欄を `a, b` の順に書くと、右端の `a` が `*2`、その左の `b` が `*1` になる。

番号は描いた順（左から）のままにした。読者が見るのは図であって定義ではなく、図の中の印は左から `*1`、`*2` と読めるのが自然で、図の下の脚注の並びとも合う。定義の順で振る選択肢（例えば `footnote_order` の設定）は足していない。オブジェクトヘッダで脚注になるのは `frozen` 1 つなので、本の図で問題になる場面がまだ無いため。この扱いは `docs/format.md` の Label fitting に 1 文書いた。

## B5. 欄の下の注記行と、行の見出し

### 読んだところ

左の欄（gutter）は、行ごとのオフセットを出すためだけにある。幅は `Svg::Geometry#measure_header` が `Layout::Result#offset_label` の最大幅 + 12 で決め、`layout.offsets: none`（既定）なら 0。描くのは `Decorations#draw_offset`。ASCII は `Renderers::Ascii` の `@offset_width`（文字数で数えていた）と `gutter`。行の下に何かを足す仕組みは無く、行の y は `Svg#draw_rows` で行の高さを足していくだけ。B4 で引き出し線の帯のために `Geometry` に `band_heights`（行の下の帯の高さ）を足したので、注記行も同じ帯に入れればよい。

### 定義の書き方の判断

計画の案を出発点に、次のように決めた。

**行の見出しは `layout.row_labels`（論理行ごとの文字列の配列）にした。** 欄に `row_label` を持たせる案は採らなかった。理由は 3 つ。(1) 左の欄はもともと「行」に属するもの（`offset_label(row)`）で、行の番号で引く配列がそのまま置き換えになる。欄に持たせると、行をまたぐ欄や結合した行（block）でどの行に出すかを決める規則が要る。(2) `Model::Field` に項目を足すと、題の無い図の id のハッシュ（`default_prefix` が `fields.map(&:to_h)` を入れる）が、使っていない定義でも変わる。`layout` の中のキーなら、書かない限りハッシュに入らない。(3) オフセットの代わりに使う、という計画の意図にも合う。配列が行より短ければ、残りの行はオフセット（`offsets: none` なら空）を出す。

ENTER の図の左上にある「bit」（ビット番号の行の見出し）のために `layout.bit_numbers_label` も足した。計画には無いが、行の見出しを使う図ではビット番号の行だけが見出し無しになり、既存の図と同じ内容にならないため。

**注記行はトップレベルの `annotations`（配列）にした。** 1 項目が 1 行で、`values`（欄 id → 文字列か整数）、`label`（左の欄に出す行の名前）、`per_bit`、`style`、`fill`。

- `per_bit: true`: 「例のビット列」は欄ごとではなくビットごとの値なので、欄 id → 文字列の対応のまま、文字列を 1 ビット 1 文字として割る形にした。文字列は上位ビットから書く（2 進数を書く向き）。長さが欄の幅と違えば V-03。行全体を 1 本の文字列で書く案（`bits: "000010000011..."`）も考えたが、欄との対応が目で追えず、欄を足したときに全部ずれるのでやめた。
- `style: plain`: 「ダンプの順」と「1bit／5bit」は枠を描かない。既定は `boxed`（枠あり）。
- `fill`: 「欄の値」の灰色。既定はテーマの `cell_fill`。
- 欄 id は、明示した `id` か名前から作ったもの（`Normalizer` の規則）。検証（`Validator`）でも同じ id が要るので、id を作る処理を `Config.field_ids` に移し、`Normalizer` と `Validator` の両方から呼ぶようにした。挙動は変えていない（md5 で確認）。
- 行をまたぐ欄では、値は最初の部分（`part` が `whole` か `head`）の下に出す。`per_bit` は欄といっしょに割り、上位の文字が上位のビットの部分へ行く。`field_order: lsb_first` では最初に置かれる部分が下位なので、文字列の後ろから取る（`Annotations#annotation_bits`。rspec で両方の向きを確かめた）。

`values` は「キーがデータのオブジェクト」で、既存の `Validator` はこれを検査できなかった（`additionalProperties` は `false` の場合しか見ていない）。スキーマには `propertyNames`（id の形）、`additionalProperties`（値の型）、`maxProperties` を書き、`Validator#check_map` でそれを検査するようにした。スキーマと `Validator` の判定が揃っていることは、`json_schemer` で 5 通りの不正な形を比べる rspec で確かめた。

`Model::Document` には `annotations` を足した。これも `default_prefix` のハッシュに入るので、空のときはハッシュから外し、題の無い図の id が変わらないようにした（B3 の id `bitgram-408ce7c0-diagram` が変わらないことを rspec に入れた）。注記がある図の id は変わる（中身が違う図なので、それでよい）。

### 描き方

注記行は 1 行が `svg.row_height` の高さで、各行の下（引き出し線の帯の下）に、定義の順に並ぶ。新しい高さの設定は作らず、既存の `row_height` を使った。行の見出しと注記行の名前は、オフセットと同じ描き方（右寄せ、`header_text` の色）で左の欄に出し、左の欄の幅はそれらの最長に合わせる。

枠の中の文字が長いときは、欄の名前と同じく 0.5px ずつ `min_font_size` まで縮め、それでも入らなければ切って V-09 を出す（`FIT_ORDER = single shrink truncate`）。最初はこれを plain にも使ったが、ENTER の「1bit」が 1bit の欄（内幅 12px）に入らず「…」に切られた。既存の図では「1bit」は隣にはみ出して描かれている。plain には守るべき枠が無いので、枠の全幅に入るまで縮め、`min_font_size` でも入らなければ切らずにはみ出させることにした（`plain_fit`）。

ASCII でも描く。注記があるときは各行の下の罫線を閉じてから、注記行を罫線無しで欄の中央に書く（行どうしが罫線を共有したままだと、注記行が箱の中に見えるため）。欄より長い文字は行の残りを右へ押す。ASCII の左の欄の幅は、今まで `String#size` で数えていたのを表示幅（`AsciiMeasurer`）にした。日本語の見出しで桁がずれるため。オフセットは ASCII の数字なので、既存の出力は変わらない（md5 で確認）。

### 描いた図

**ENTER**（`impl-b4b5/enter_aspec.yml`）。欄の並びと位置は `include/mruby/proc.h:92-99` の `MRB_ASPEC_*`（4.1.0-rc2）で確かめ、例のダンプは `docker run kishima/mruby:4.1.0-rc2 mrbc --verbose` で実際に出した。

```
$ docker run --rm -v $PWD:/w kishima/mruby:4.1.0-rc2 mrbc --verbose /w/enter_sample.rb | grep -m2 ENTER
```

既存の図の 1 行目「ENTER の Operand は 24bit（W 形式）。ダンプの 8 つの数字はこの 8 つの欄の値」は描いていない。bitgram の題は 1 行だけなので、例の行（`例: def f1(...) → ENTER 2:1:1:1:1:1:1:0 (0x83087)`）を題にし、1 行目は図の下の説明文と同じく本文に置く前提にした。題が図の幅より長いと左右にはみ出す（bitgram は題の幅を図の幅に入れない）ので、この図だけ `svg.bit_width: 32` にした。この値は題が入る幅として選んだだけで、本で使う寸法は B6 で決める。

## 気づいた点（範囲外。直していない）

- **題の幅が図の幅に入らない**（`Svg::Geometry#initialize` の `@width` は余白と左の欄とビットの幅だけ）。長い題は SVG の外にはみ出して切れる。ENTER の図で踏み、`bit_width` を広げて逃げた。属する先: bitgram の挙動（本家にもある）。本の図では題を使わずキャプションに回すなら問題にならない。
- **ENTER の図は本文幅に入らない**。`bit_width: 32` で 684pt、`bit_width` 既定の 20 でも約 463pt で、本文幅（約 441pt）を超えて縮小される。文字の大きさ・`bit_width` の本の既定値は B6 で、図の幅から決める必要がある。属する先: B6。
- **「…」のような、ビット番号を付けたくない欄の上にもビット番号が出る**。Word Boxing では `bit_numbers: false` にしたので、下位 8bit に 7〜0 の番号が無い。番号を欄ごとに消す、または番号の起点をずらす設定が要るかは著者の判断。属する先: 計画（B5 の追加か、本では番号無しでよいか）。
- **欄の名前を太字にする設定が無い**（既存の draw.io の図は欄の名前が太字）。並べて浮くかは著者が PNG で判断する。属する先: B6 か計画。
- **ASCII で plain の注記が欄より長いと、行の残りが右へずれる**（ENTER の「1bit」）。本の図は SVG／PDF なので影響は無い。属する先: bitgram の ASCII 出力。
- **`svg.fit_order` の値 `vertical` は `ascii.max_label_lines` を上限に使う**（`Svg#fit_cell`）。SVG の設定が ASCII の節の値に左右されるのは分かりにくい。B4 で `vertical` を「縦書き」に使わなかった理由の 1 つ。属する先: 本家の bitgram。
